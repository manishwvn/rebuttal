# Deploying Rebuttal to Render

Everything the code needs is in [`render.yaml`](../render.yaml). You do the steps that need your accounts; none of them
needs a secret to go through chat or git. Sandbox only: the app refuses a live PayPal URL.

Do these in order. Total: about 30 minutes.

## 0. What you need open

- `backend/.env` in an editor (to copy values from; do not paste them anywhere public).
- Accounts: Render, GitHub (repo `manishwvn/rebuttal`), PayPal Developer (sandbox app).

## 1. Claim the $50 Render hackathon credits

I could not verify how the credit is issued, so check the source rather than trusting these steps blindly.

1. Find the Render credit in the hackathon's own materials: the Devpost page (Resources / Perks / Sponsors) or the
   participant email. It is normally a promo code or a claim link.
2. Create or log in to your account at <https://dashboard.render.com>.
3. Apply it in Render: **Account / Workspace Settings > Billing**, then the credits or promo code field (the exact
   label may differ).
4. `render.yaml` uses the **free** plan, so the credit is optional. Keep it for upgrading to an always-on paid
   instance (`plan: 0.5c-512mb`, roughly $7/month, so $50 covers it through Dec 15) if the cold starts below bother you.

## 2. Deploy from GitHub

1. Render dashboard > **New +** > **Blueprint**.
2. **Connect GitHub**, allow access to the `manishwvn/rebuttal` repository, select it, branch `main`.
3. Render reads `render.yaml` and shows one service, `rebuttal-api`. (Our live service was created by hand in the dashboard and is named `rebuttal`, hence `rebuttal-oq3g.onrender.com`; the yaml keeps `rebuttal-api` for anyone redeploying from the blueprint.)
4. It asks for every secret marked `sync: false`. Fill them (copy from `backend/.env`; names match):

   | Variable | Value |
   |---|---|
   | `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` | your PayPal **sandbox** app keys |
   | `GROQ_API_KEY` | your Groq key (the live model) |
   | `DATABASE_URL` | the Supabase **session pooler** URL, port 5432 (the one already in `.env`) |
   | `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` | your Langfuse keys (leave empty to run without tracing) |
   | `PAYPAL_WEBHOOK_ID` | leave empty for now; you get it in step 3 |

   `REBUTTAL_API_TOKEN` is generated by Render; do not fill it.
5. **Apply** / **Deploy Blueprint**. The first build takes a few minutes.
6. When it is live, copy the service URL, ours is `https://rebuttal-oq3g.onrender.com`.
7. Check it: open `https://rebuttal-oq3g.onrender.com/api/health`. Expect `{"ok": true, "mode": "sandbox / groq", "auth": true, "database": true}`.
   `database: true` means Supabase answered; `mode` ending in `groq` means the live model is Groq.
8. Read the API token: service > **Environment** > `REBUTTAL_API_TOKEN` > reveal. API calls need
   `Authorization: Bearer <token>`.

Changing an environment variable in Render redeploys the service automatically.

## 3. Register the webhook in the PayPal sandbox

1. <https://developer.paypal.com/dashboard/applications/sandbox>, open the same sandbox app whose keys you used.
2. Scroll to **Sandbox Webhooks** > **Add Webhook**.
3. **Webhook URL**: `https://rebuttal-oq3g.onrender.com/api/webhooks/paypal` (must be https; Render gives you that).
4. **Event types**: tick everything under **Disputes** (`CUSTOMER.DISPUTE.CREATED`, `.UPDATED`, `.RESOLVED`; the
   "Customer dispute" group). Only `CREATED` starts an analysis today; the others are accepted and ignored.
5. **Save**. PayPal shows a **Webhook ID**. Copy it.
6. Render > your service > **Environment** > set `PAYPAL_WEBHOOK_ID` to that id > **Save**. It redeploys.

Until the id is set, the real-sandbox app answers webhooks with 503 on purpose (it will not accept unverified
deliveries). To test: file a dispute as the sandbox buyer, or use PayPal's **Webhooks simulator**. Note PayPal says
simulator events carry no genuine signature, so they are expected to fail verification (401); a real dispute should
pass. Then look at `https://rebuttal-oq3g.onrender.com/api/disputes` (with the bearer token) for the new proposal waiting for approval.

## 3b. Test it with a live dispute (what we did on Oct 7)

1. Set `REBUTTAL_MOCK=0` in Render (the blueprint already does) and `PAYPAL_WEBHOOK_ID` as in step 3.
2. On your machine: `cd backend && uv run python -u -m scripts.make_test_order --case agent_wrong_size`. It creates a
   sandbox order whose invoice id is `RB-agent_wrong_size-<timestamp>`, prints the buyer approval link, waits for you
   to approve it as the sandbox buyer, captures the payment and adds the case's tracking number. The agent maps that
   invoice pattern to the seeded merchant record (so `order_found` is true and the buyer's AI-assistant instruction
   is known). Real orders do not match the pattern. These records are flagged `demo_fixture` (in the facts and the audit trail), and
   their order date is relative to when the dispute is gathered, so duplicate-charge facts are not reliable for them.
3. File a dispute as the sandbox buyer on that payment in the sandbox Resolution Center ("item not as described").
4. The first dispute event took about 4 minutes to arrive from the sandbox. If the free instance is asleep at that
   moment it may miss the first delivery; PayPal retries, and repeating an analysis is harmless.
5. Check `https://rebuttal-oq3g.onrender.com/api/proposals/pending` (bearer token) or the `rebuttal_audit` table in
   Supabase: the proposal waits for approval; nothing was written to PayPal.
6. Events from PayPal's **Webhooks simulator** get 401 by design: they cannot be signature-verified.

## 4. Supabase keep-alive (GitHub variable)

1. GitHub > the `rebuttal` repo > **Settings** > **Secrets and variables** > **Actions** > **Variables** tab >
   **New repository variable**.
2. Name `APP_HEALTH_URL`, value `https://rebuttal-oq3g.onrender.com/api/health` (include the `/api/health`). Save.
3. **Actions** tab > **keep-supabase-awake** > **Run workflow** to test; it should go green. It then runs daily, and
   each ping runs `SELECT 1` on Supabase, which keeps the free project from being paused.

(Alternative with no deployed app: a repository **secret** `SUPABASE_DB_URL` with the Supabase URL; the workflow then
queries the database directly. Leave `APP_HEALTH_URL` unset in that case.)

## Public demo routes

The `/api/demo/...` routes take no token, by design: judges have no PayPal accounts. They reach only per-visitor mock
sessions, never the real sandbox, the database or the approval queue (see [demo-mode.md](demo-mode.md)). Because they
are open, they are bounded:

- 40 live sessions; the least recently used is evicted when a 41st starts.
- 20 session creations or resets per minute for the whole service. So one client can use up the window and lock judges
  out for up to a minute, or push their sessions out through eviction. Accepted for the hackathon; there is no
  per-client limit.
- 16 disputes and 100 workflow runs per session (analyze, approve, reject, retry, simulate). Each run adds to the
  session's memory, so the budget keeps one client from filling the 512 MB of the free plan, which the webhook and
  approval queue share. Reset demo restores it.
- Sessions live in memory only and expire after 30 minutes idle or 2 hours of age.

## Notes and open items

- **Free plan trade-offs:** the service sleeps after 15 idle minutes and wakes on the next request, which takes about
  a minute. A PayPal webhook that arrives while it sleeps may time out; PayPal retries deliveries, and the analysis is
  safe to repeat (a second analysis of the same dispute does nothing). Judges opening the app cold should expect that
  wait. The daily keep-alive ping keeps Supabase awake but does not keep Render awake.
- Mock instead of the real sandbox: set `REBUTTAL_MOCK=1` in Render. Then the in-memory sandbox plus the judge
  simulator (`/api/simulator/dispute/{case}`) run, and webhooks are accepted without a webhook id.
- Not verified here: the `uv` build/start commands on Render (Render documents `uv.lock` support but not these exact
  commands), and whether 512 MB is enough. If the build fails, read the build log and tell me the first error.
- The NVIDIA and Anthropic keys are not needed on Render. Do not set `ANTHROPIC_API_KEY` there: it would win over
  Groq.
